# 04. 협업 규칙 — 이슈 · 브랜치 · PR

모든 작업은 **이슈 → 브랜치 → PR → 머지** 순서로 기록을 남긴다.

## 0. 단계 진행 방식 (한 번에 한 단계)

```
① 계획 제안 ──(사용자 OK)──▶ ② 구현·PR ──▶ ③ 함께 리뷰 ──(사용자 머지)──▶ 다음 단계 ①
```

| 단계 | Claude | 사용자 |
|---|---|---|
| ① 계획 제안 | 무엇을·왜 만드는지, 바뀔 파일, 완료 조건, 확인 방법을 짧게 설명 | OK / 수정 요청 |
| ② 구현·PR | 이슈 생성 → 브랜치 → 구현 → 테스트 → PR. 단계 안의 사소한 결정은 직접 판단하고 PR에 적음 | — |
| ③ 함께 리뷰 | 바뀐 점을 쉽게 설명하고, 직접 확인할 순서를 안내. 질문·수정 요청 반영 | 확인, 질문, 머지 |

- 한 단계는 보통 `docs/03_MVP.md`의 백로그 항목 하나(예: M0-1)다. 너무 크면 나눠서 제안한다.
- 머지 전에는 다음 단계를 시작하지 않는다.

## 1. 흐름

1. **이슈 만들기**: 할 일 하나에 이슈 하나. 백로그 ID(예: `M1-5`)가 있으면 제목에 적는다.
2. **브랜치 만들기**: 최신 `main`에서 아래 규칙대로 만든다.
3. **커밋**: 작게 자주. 메시지에 이슈 번호를 적는다(`(#12)`).
4. **PR 열기**: 본문에 `Closes #이슈번호`를 적어, 머지되면 이슈가 자동으로 닫히게 한다.
5. **검수와 머지**: 사용자(검수자)가 확인하고 머지한다. 머지 방식은 **Squash and merge**를 기본으로 한다(`main` 기록이 PR 단위로 깔끔하게 남음).
6. 머지된 브랜치는 삭제한다.

`main`에 직접 푸시하지 않는다. (예외: 저장소의 첫 커밋, 이슈 #1)

## 2. 브랜치 이름

```
<이슈번호>/<종류>-<영역>-<설명>
```

| 부분 | 값 | 예 |
|---|---|---|
| 이슈번호 | 숫자만 | `12` |
| 종류 | `feat` 새 기능 · `fix` 버그 · `docs` 문서 · `refactor` 리팩터링 · `test` 테스트·평가 · `chore` 설정·빌드 | `feat` |
| 영역 | `ai` LLM·프롬프트·기억 파이프라인 · `fe` 프론트엔드 · `be` 백엔드·DB·API · `common` 여러 영역·문서·설정 | `fe` |
| 설명 | 영어 소문자, 단어는 `-`로 연결, 3~5단어 | `chat-streaming-ui` |

예시
- `12/feat-fe-chat-streaming-ui`
- `15/feat-ai-memory-extraction`
- `18/fix-be-rewind-invalidation`
- `2/docs-common-git-workflow`

브랜치 이름 맨 앞에 `#`를 붙이지 않는다. 터미널에서 `#` 뒤는 주석으로 처리되어 명령이 깨지기 때문이다.

## 3. 커밋 메시지

```
<종류>(<영역>): <요약> (#이슈번호)

(선택) 본문: 무엇을, 왜
```
예: `feat(ai): 기억 추출 결과를 Zod 스키마로 검증 (#15)`

## 4. 라벨

- 종류: `feat` `fix` `docs` `refactor` `test` `chore`
- 영역: `area:ai` `area:fe` `area:be` `area:common`

이슈와 PR에 종류 하나, 영역 하나 이상을 단다.

## 5. PR 본문

`.github/pull_request_template.md`를 따른다. 요약, 관련 이슈, 변경 사항, 확인 방법, 체크리스트로 구성된다. 화면이 바뀌면 스크린샷을 붙인다.
