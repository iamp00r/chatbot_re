## 개요

Supabase Auth로 **Google 로그인**과 **이메일 매직링크**를 붙였다. 로그인하지 않은 사용자는 `/login`으로 가고, 처음 로그인하면 `/onboarding`에서 닉네임을 받아 `profiles` 행을 만든 뒤 홈으로 간다. 이제 이후 기능(M1 캐릭터·작품·채팅)이 "현재 사용자"를 전제로 만들어질 수 있다.

```
비로그인 → /login ─(Google | 메일 링크)→ Supabase → /auth/callback → 세션 쿠키
         → /  ─(profiles 없음)→ /onboarding → 닉네임 저장 → /  "하늘님, 반가워요."
```

## 구현 내용

### 1. Supabase 클라이언트 세 종류 (`src/lib/supabase/`)

| 파일 | 어디서 | 쿠키 처리 |
|---|---|---|
| `client.ts` | 브라우저(클라이언트 컴포넌트) | 브라우저 `document.cookie` |
| `server.ts` | 서버 컴포넌트·서버 액션·라우트 핸들러 | `next/headers`의 `cookies()` |
| `proxy.ts` | `src/proxy.ts`(모든 요청 앞) | `request.cookies` → `response.cookies` |

세 클라이언트 모두 **anon 키 + 사용자 JWT**로 접속한다. 그래서 DB 요청에 RLS가 그대로 걸린다. 서비스 롤 키는 쓰지 않는다.

```ts
// server.ts
export async function createClient() {
  await connection();                 // 요청 시점 렌더링임을 밝힌다(아래 "문제와 해결" 2)
  const cookieStore = await cookies();
  const { url, anonKey } = requireSupabaseEnv();
  return createServerClient(url, anonKey, {
    cookies: {
      getAll: () => cookieStore.getAll(),
      setAll(cookiesToSet) {
        try { for (const c of cookiesToSet) cookieStore.set(c.name, c.value, c.options); }
        catch { /* 서버 컴포넌트 렌더링 중에는 쿠키를 못 쓴다. 갱신은 proxy 담당 */ }
      },
    },
  });
}
```

### 2. proxy (`src/proxy.ts` → `src/lib/supabase/proxy.ts`)

Next.js 16에서 `middleware.ts`는 폐기되고 **`proxy.ts`**로 이름이 바뀌었다(기본 런타임 Node.js). 하는 일은 두 가지다.

1. **세션 갱신**: access token(1시간)이 만료되면 refresh token으로 새 토큰을 받아 쿠키에 다시 쓴다. 서버 컴포넌트는 쿠키를 쓸 수 없으므로 이 일은 proxy만 할 수 있다.
2. **이동 결정**: 비로그인 + 비공개 경로 → `/login?next=원래경로`, `/api/*`는 401. 로그인 상태로 `/login`에 오면 `/`로 보낸다.

```ts
setAll(cookiesToSet, headers) {
  for (const { name, value } of cookiesToSet) request.cookies.set(name, value); // 이후 렌더링이 새 토큰을 읽도록
  response = NextResponse.next({ request });
  for (const { name, value, options } of cookiesToSet) response.cookies.set(name, value, options); // 브라우저 저장
  for (const [k, v] of Object.entries(headers)) response.headers.set(k, v); // Cache-Control: no-store 등
}
...
const { data } = await supabase.auth.getClaims();   // JWT 검증
```

- 리다이렉트할 때도 갱신된 쿠키와 캐시 금지 헤더를 옮겨 담는다(안 그러면 갱신된 토큰을 잃는다).
- `/api/health`는 Supabase를 아예 부르지 않고 통과시킨다(keepalive용, 명세 §9 예외).
- Supabase 환경 변수가 없으면(CI 빌드 등) "로그인 안 됨"으로 처리한다 — 실패해도 닫힌 쪽으로.

### 3. 데이터 접근 계층 DAL (`src/lib/auth/dal.ts`)

proxy 검사는 **낙관적 검사**다. Next.js 문서도 proxy만으로 권한을 처리하지 말라고 한다(matcher 실수, 서버 액션 직접 호출 등으로 우회될 수 있음). 그래서 보호가 필요한 화면·서버 액션은 반드시 DAL을 거친다.

```ts
export const getSessionUser = cache(async () => { /* getClaims → {id, email, metadata} | null */ });
export const getProfile = cache(async (userId) => { /* profiles에서 본인 행 */ });
export async function requireUser()    { /* 없으면 redirect("/login") */ }
export async function requireProfile() { /* 프로필 없으면 redirect("/onboarding") */ }
```

`react`의 `cache`로 한 요청 안에서는 한 번만 조회한다.

### 4. 화면과 라우트

- **`/login`** (`login-form.tsx`, 클라이언트 컴포넌트)
  - Google: `signInWithOAuth({ provider: "google", options: { redirectTo: <origin>/auth/callback?next=… } })`
  - 매직링크: `signInWithOtp({ email, options: { emailRedirectTo: 같은 주소 } })` → "메일을 보냈습니다" 표시
  - `?error=`는 고정된 문구 표에서만 골라 보여 준다(주소에 쓴 글자가 화면에 그대로 나오지 않게).
- **`/auth/callback`** (`route.ts`)
  - `?code=` → `exchangeCodeForSession(code)` (Google, 기본 메일 양식의 매직링크)
  - `?token_hash=&type=` → `verifyOtp(...)` (메일 양식을 바꿨을 때. 아래 "설계 결정")
  - 성공 → `safeNextPath(next)`로 이동, 실패 → `/login?error=callback`
- **`/onboarding`** + 서버 액션 `createProfile`
  - Google 이름(`user_metadata.name`)으로 입력칸을 미리 채운다.
  - Zod로 닉네임 검사(앞뒤 공백 제거, 1~20자, 제어 문자 금지).
  - `profiles`에 `{ id: user.id, nickname, avatar_url }` insert. RLS `profiles_own`(`id = auth.uid()`)이 남의 id를 막는다. 중복(23505)은 다른 탭에서 먼저 만든 경우라 그대로 진행.
- **홈 `/`**: `requireProfile()` → "닉네임님, 반가워요." + 로그아웃 버튼(서버 액션 `signOut`).

### 5. 오픈 리다이렉트 방지 (`src/lib/auth/paths.ts`의 `safeNextPath`)

`next`는 사용자가 주소창에 마음대로 넣을 수 있다. 검사하지 않으면 `?next=//evil.com`으로 로그인 직후 피싱 사이트로 보낼 수 있다.

```ts
if (!next || !next.startsWith("/") || next.startsWith("//") || next.startsWith("/\\")) return "/";
if (/[\u0000-\u001f\u007f]/.test(next)) return "/";          // 탭·줄바꿈(URL 파서가 지워 버림)
const url = new URL(next, "http://loom.invalid");
if (url.origin !== "http://loom.invalid") return "/";
if (url.pathname.startsWith("//") || url.pathname.includes("\\")) return "/"; // 정규화 결과도 확인
```

## 동작 방식

### Google 로그인 (PKCE)
```
브라우저 /login ── signInWithOAuth ──▶ (code_verifier를 쿠키에 저장) ─▶ Google 동의 화면
   ▲                                                                    │
   │                    Supabase /auth/v1/callback ◀────────────────────┘
   │                          │ ?code=…
   └── 302 next ◀── /auth/callback: exchangeCodeForSession(code + 쿠키의 verifier) → 세션 쿠키 저장
```
PKCE: 로그인을 시작한 브라우저만 가진 비밀값(verifier)이 있어야 code를 세션으로 바꿀 수 있다. code가 가로채져도 소용없다.

### 매 요청
```
요청 → proxy: getClaims(필요하면 토큰 갱신) → 공개 경로? 로그인? → 통과/이동
     → 페이지: <Suspense> 안에서 requireProfile() → RLS가 걸린 조회 → 렌더링
```

## 설계 결정

| 결정 | 선택 | 대안 | 이유 |
|---|---|---|---|
| 세션 확인 함수 | `getClaims()` | `getSession()` | `getSession`은 쿠키 값을 검증 없이 믿는다. `getClaims`는 JWT 서명을 검증한다(비대칭 키면 로컬 검증, 구형 대칭 키면 Auth 서버에 `getUser` 왕복) |
| 권한 확인 위치 | proxy(낙관적) + DAL(실제) + RLS(최종) | proxy에서만 | Next.js 권장. 한 곳이 뚫려도 다음 층이 막는다 |
| 로그인 시작 위치 | 클라이언트 컴포넌트 | 서버 액션 | `window.location.origin`으로 미리보기·로컬·운영 주소를 자동으로 맞춘다. 돌아올 주소는 Supabase의 Redirect URLs 허용 목록이 한 번 더 검사한다 |
| 매직링크 확인 | 기본 메일 양식(`?code=`) + `token_hash`도 지원 | 메일 양식을 `token_hash`로 바꾸기 | 사용자 쪽 새 설정 없이 동작. 다만 **링크를 요청한 브라우저에서 열어야** 한다(PKCE verifier가 그 브라우저 쿠키에 있음). 다른 기기에서도 열리게 하려면 Supabase 메일 양식을 바꾸면 된다(아래 "참고") — 콜백은 이미 지원 |
| 프로필 생성 시점 | 첫 화면 진입 시 온보딩에서 | DB 트리거(`auth.users` insert 시 자동) | 닉네임을 사용자에게 받아야 한다(인수 조건). 트리거로 만들면 임시 닉네임이 생긴다 |
| 프로필 없을 때 이동 | 페이지의 DAL(`requireProfile`) | proxy에서 DB 조회 | proxy는 모든 요청에 돌기 때문에 DB 조회를 넣으면 느려진다. Next.js도 proxy에서 느린 조회를 하지 말라고 한다 |
| 비로그인 API 요청 | 401 JSON | `/login`으로 이동 | fetch가 로그인 HTML을 받으면 오류 원인이 숨는다 |
| E2E에서 로그인 | 가짜 Supabase 서버 | 실제 Supabase 테스트 계정 | CI에 비밀값이 필요 없고, 결과가 항상 같다 |

## 문제와 해결

1. **빌드 실패: "NEXT_PUBLIC_SUPABASE_URL이 없습니다"** — 빌드 때 `/`를 미리 렌더링하다가 `createClient()`가 환경 변수부터 검사해서 오류가 났다. Cache Components에서는 `cookies()`를 부르는 순간 그 부분이 "요청 시점 렌더링"으로 넘어가 빌드 때 렌더링이 멈춘다. 그래서 `cookies()`를 환경 변수 검사보다 **먼저** 부르게 순서를 바꿨다.
2. **실행 중 경고: "unstable value `Date.now()` while prerendering"** — 로그인한 사용자가 `/`를 열 때 나왔다. Supabase가 토큰 만료를 `Date.now()`와 비교하는데, Cache Components는 쿠키를 읽은 뒤에도 "지금 시각"은 따로 허락받아야 한다(프리페치 단계에서 미리 그릴 수 있기 때문). `await connection()`을 맨 앞에 두어 해결했다.
3. **열린 리다이렉트 구멍** — 처음 `safeNextPath`는 입력이 `//`로 시작하는지만 봤다. 단위 테스트에서 `/../..//evil.example`이 URL로 정리되면서 `//evil.example`(프로토콜 상대 주소 = 다른 사이트)이 되는 것을 찾았다. 정리된 결과도 다시 검사하게 고쳤다.
4. **E2E: `getByRole("alert")`가 두 개** — Next.js가 페이지 이동을 화면 낭독기에 알리는 `#__next-route-announcer__`도 `role="alert"`다. 글자로 찾게 바꿨다.

## 개념 정리

- **세션 쿠키와 JWT**: Supabase 로그인 결과는 access token(JWT, 1시간)과 refresh token이다. `@supabase/ssr`은 이것을 `sb-<프로젝트>-auth-token` 쿠키에 넣는다(길면 `.0`, `.1`로 나눔). JWT는 누구나 읽을 수 있지만 서명은 Supabase만 만들 수 있어, **서명 검증**이 곧 신원 확인이다.
- **PKCE(Proof Key for Code Exchange)**: 로그인 시작 시 임의의 verifier를 만들고 그 해시(challenge)만 Supabase에 보낸다. 돌아온 code를 세션으로 바꿀 때 verifier 원본을 함께 내야 한다. code를 훔쳐도 verifier가 없으면 쓸 수 없다.
- **RLS(Row Level Security)**: Postgres가 행마다 정책을 검사한다. anon 키 + 사용자 JWT로 접속하면 `auth.uid()`가 그 사용자 id가 된다. 앱 코드가 실수해도 DB가 남의 행을 막는 마지막 방어선이다.
- **proxy(구 middleware)**: 라우트가 렌더링되기 전에 모든 요청에서 돈다. 리다이렉트·헤더·쿠키 조작에 적합하고, 느린 조회나 최종 권한 판단에는 맞지 않는다. `matcher`로 정적 파일을 빼야 한다.
- **Cache Components와 Suspense**: `cacheComponents: true`면 정적인 부분은 빌드 때 미리 그리고(정적 껍데기), 쿠키·현재 시각 같은 요청 시점 값을 쓰는 부분은 `<Suspense>` 안에서 요청 때 스트리밍한다. 그래서 세션을 읽는 컴포넌트는 모두 `<Suspense>` 안에 두었고, 제목처럼 고정된 부분은 즉시 보인다.
- **서버 액션은 공개 엔드포인트**: `"use server"` 함수는 폼이 아니어도 누구나 POST로 부를 수 있다. 그래서 `createProfile`은 화면 검사와 별개로 `requireUser()`를 다시 부른다. Next.js는 Origin 헤더 검사로 다른 사이트에서의 호출(CSRF)을 막는다.
- **오픈 리다이렉트**: 신뢰할 수 있는 사이트 주소를 미끼로 피싱 사이트로 보내는 공격. "같은 사이트 안의 경로만 허용"을 정리된 결과까지 확인해야 한다.
