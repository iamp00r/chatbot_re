# M0-2 DB 테이블과 보안 규칙(RLS)

> 앱이 저장할 모든 데이터의 칸(테이블)을 만들고, "자기 것만 보이게" 하는 보안 규칙을 DB에 걸었다 · PR #12 · 2026-11-27

## 한 줄로

캐릭터·작품·채팅·기억을 저장할 **테이블 20개**를 Supabase(서울)에 만들고, **다른 사람의 채팅이나 기억은 DB 차원에서 절대 읽을 수 없게** 막았다.

## 무엇을 만들었나

- 테이블 만들기 SQL (`supabase/migrations/…_init_schema.sql`)
- 데이터가 꼬이지 않게 막는 장치(트리거) (`…_integrity.sql`)
- 보안 규칙 RLS (`…_rls.sql`)
- 위 셋이 제대로 동작하는지 확인하는 테스트 (`supabase/tests/`, `scripts/db-test-local.sh`)
- 앱 코드에서 DB를 쓰기 위한 연결과 테이블 지도 (`src/lib/db/client.ts`, `schema.ts`) + 지도와 실제 DB가 같은지 확인하는 테스트

### 테이블 묶음

| 묶음 | 테이블 | 담는 것 |
|---|---|---|
| 사용자 | `profiles`, `personas` | 닉네임, 대화할 때 내가 연기할 인물 |
| 만들기 | `characters`, `stories`, `story_characters` | 캐릭터 설정, 작품(세계관·인트로), 작품에 나오는 캐릭터 |
| 원작 기억 | `canon_nodes`, `canon_edges`, `canon_memories` | 작품 주인이 미리 정해 둔 인물·관계·사실 |
| 채팅 | `rooms`, `room_participants`, `messages` | 채팅방, 참여 캐릭터, 메시지(재생성 변형 포함) |
| 기억 | `mem_nodes`, `mem_edges`, `memories`, `memory_subjects`, `memory_knowers` | 대화에서 생긴 인물·관계·사건, 그리고 **누가 그걸 아는지** |
| 자동 작업 | `memory_ops`, `memory_jobs`, `room_summaries`, `generation_logs` | AI가 기억을 바꾼 기록, 작업 대기열, 줄거리 요약, AI 호출 기록(토큰·비용) |

## 어떻게 동작하나

**RLS(행 단위 보안)**: 테이블마다 "이 줄을 누가 볼 수 있나" 규칙을 단다.

```
사용자 A가 messages 테이블을 조회
  → DB가 줄마다 확인: "이 메시지의 채팅방 주인이 A인가?"
  → A의 방 메시지만 돌려준다. B의 메시지는 존재하지 않는 것처럼 보인다
```

- 로그인 안 한 사람에게는 아무 규칙도 주지 않았다 → 아무것도 못 본다.
- AI 자동 작업용 테이블(기억 변경 기록, 요약, AI 호출 기록)은 사용자가 **읽기만** 가능하다. 쓰기는 서버만 한다.

**정합성 트리거**: 잘못된 데이터가 들어오려 하면 DB가 거절한다. 예:
- 기억의 "아는 사람"으로 사물이나 장소를 지정 → 거절 (인물만 가능)
- 다른 채팅방의 인물을 관계로 연결 → 거절
- 같은 방에 "김철수"와 "김 철수"(띄어쓰기만 다름) 노드 → 거절

## 왜 이렇게 했나

| 결정 | 고른 것 | 다른 선택지 | 이유 |
|---|---|---|---|
| DB | Supabase(Postgres) | Firebase 등 | 표 구조 데이터(인물·관계)에 강한 정통 DB. 로그인·보안 규칙·파일 저장이 한곳에, 무료 플랜 |
| 지역 | 서울 | 미국(기본값) | 사용자와 가까워 응답이 빠르다 |
| 보안 | RLS + 서버 코드에서 한 번 더 확인 | 서버 코드에서만 확인 | **이중 방어.** 코드에 실수가 있어도 DB가 마지막으로 막는다. 남의 대화가 새면 치명적인 서비스라서 |
| 기준 문서 | SQL 파일이 기준, 코드 쪽 지도는 테스트로 맞춤 | 코드에서 DB를 자동 생성 | 트리거·보안 규칙은 SQL로만 정확히 쓸 수 있다. 대신 둘이 어긋나면 테스트가 잡는다 |
| 테스트 위치 | 빈 Postgres(GitHub Actions)에서 | 실제 Supabase에서 | 실제 데이터를 건드리지 않고, 키 없이 PR마다 자동으로 돈다 |
| 기억 데이터 모양 | 노드(인물·사물) + 관계 + 기억 + 아는 사람 | 대화 요약 글 하나 | 사용자가 표와 그래프로 보고 고칠 수 있고, 캐릭터별로 "아는 것만" 골라 줄 수 있다 (이 서비스의 핵심) |
| 임베딩(벡터) 확장 | 미리 켜만 둠 | MVP에서 사용 | MVP는 규칙 점수로 검색한다. 나중에 쓰려고 확장만 준비 |

## 사용자가 한 일

- Supabase 가입, 서울 지역 프로젝트 생성
- SQL 편집기에서 마이그레이션 3개 실행
- 내 컴퓨터 `.env.local`에 Supabase 키 3개와 `DATABASE_URL` 입력
- Google OAuth 제공자 켜기 (M0-3 준비)

## 확인한 방법

- RLS 테스트: 사용자 A·B를 만들어 A가 B의 방·메시지·기억을 읽거나 고칠 수 없는지, 로그인 안 한 사람은 아무것도 못 보는지
- 정합성 테스트: 위의 잘못된 데이터들이 실제로 거절되는지
- 둘 다 PR마다 `DB` 검사로 자동 실행

## 용어 풀이

| 용어 | 뜻 |
|---|---|
| 테이블 | 엑셀 시트 같은 표. 줄 하나가 데이터 하나 |
| 마이그레이션 | DB 구조를 바꾸는 SQL 파일. 순서대로 실행하면 어디서든 같은 DB가 된다 |
| RLS (Row Level Security) | 줄(행) 하나하나에 "누가 볼 수 있나"를 거는 DB 보안 규칙 |
| 트리거 | 데이터가 들어오거나 바뀔 때 DB가 자동으로 실행하는 검사·동작 |
| 외래키(FK) | "이 메시지는 저 채팅방 것"처럼 테이블끼리 잇는 연결. 연결 대상이 없으면 저장이 거절된다 |
| 서비스 역할 키 | RLS를 건너뛰는 관리자 키. 서버에서만 쓰고 화면(브라우저)에는 절대 보내지 않는다 |

## 설명할 때 (30초 버전)

> 캐릭터 채팅은 남의 대화가 새면 끝이라서, 보안을 앱 코드에만 맡기지 않고 DB 자체에 행 단위 보안(RLS)을 걸었습니다. 서버 코드가 한 번, DB가 한 번 더 막는 이중 방어입니다. 기억은 글 요약이 아니라 인물·관계·사건·"누가 아는가"로 나눠 저장해서, 사용자가 표로 고치고 캐릭터마다 아는 것만 말하게 할 수 있는 구조로 만들었습니다. 이 규칙들은 PR마다 빈 DB에서 자동 테스트됩니다.
