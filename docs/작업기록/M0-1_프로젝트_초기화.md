## 개요

앱의 뼈대와 품질 장치를 만든 단계. 기능은 홈 화면("Loom") 하나뿐이지만, 이후 모든 코드가 지나갈 **검사 파이프라인**(서식 → 린트 → 타입 → 단위 테스트 → E2E)을 먼저 깔았다. main 브랜치 보호와 묶여서, 이 검사를 통과하지 못한 PR은 머지할 수 없다.

## 구현 내용

### Next.js 16 (App Router, TypeScript)
- `create-next-app`으로 생성, 소스는 `src/` 아래. 경로 별칭 `@/*` → `src/*` (`tsconfig.json`).
- `next.config.ts`
  ```ts
  cacheComponents: true,     // Cache Components: 페이지·GET 핸들러를 기본적으로 미리 렌더링
  partialPrefetching: true,
  turbopack: { rules: { "*.css": { loaders: ["@tailwindcss/turbopack"], as: "*.css" } } },
  ```
  `cacheComponents`는 M0-4에서 `/api/health`를 만들 때 실제로 영향을 줬다(아래 개념 정리, M0-4 기록 참고).
- `src/app/layout.tsx`: `<html lang="ko">`. `LayoutProps<"/">` 타입은 `next typegen`이 생성한다 → `typecheck` 스크립트가 `next typegen && tsc --noEmit`인 이유.
- 폰트: 기본 Geist는 한글 글리프가 없어 **한글 시스템 폰트 스택**으로 교체(외부 폰트 다운로드 없음).

### Tailwind CSS 4 + shadcn/ui
- `components.json`: style `new-york`, baseColor `neutral`, CSS 변수 테마(라이트·다크), 아이콘 `lucide`.
- `src/lib/utils.ts`의 `cn()` = `clsx`(조건부 클래스) + `tailwind-merge`(충돌 클래스 정리).
- `src/components/ui/button.tsx`: `class-variance-authority`(cva)로 variant·size 조합.
- 작업 환경(클라우드)에서 `ui.shadcn.com` 레지스트리가 막혀 CLI 대신 **CLI가 생성하는 것과 같은 형식으로 직접 작성**했다. 로컬에서는 `pnpm dlx shadcn@latest add <컴포넌트>`를 그대로 쓸 수 있다.

### 린트·서식
- ESLint 9 flat config: `eslint-config-next`의 `core-web-vitals` + `typescript`, 마지막에 `eslint-config-prettier`로 서식 관련 규칙을 꺼서 Prettier와 충돌을 없앴다.
- Prettier + `prettier-plugin-tailwindcss`(클래스 순서 자동 정렬).

### 테스트
- **Vitest** (`vitest.config.mts`): 환경 `jsdom`, `@testing-library/react`·`jest-dom`. 대상 `tests/unit/**`, `tests/db/**`, `src/**/*.test.*`.
- **Playwright** (`playwright.config.ts`): `webServer`가 `pnpm build && pnpm start --port 3100`로 **프로덕션 빌드**를 띄우고 테스트한다. 개발 서버에서는 안 보이는 빌드 오류·프리렌더 문제를 잡기 위해서다. CI에서는 재시도 1회, `forbidOnly`.

### CI (`.github/workflows/ci.yml`)
```
on: pull_request, push(main)
pnpm install --frozen-lockfile
→ format:check → lint → typecheck → test → playwright install chromium → e2e
concurrency: 같은 브랜치의 이전 실행은 취소
```
`--frozen-lockfile`: lockfile과 package.json이 다르면 실패 → "내 컴퓨터에선 되는데" 문제 방지.

## 동작 방식

```
PR 생성/푸시 → GitHub Actions 러너(ubuntu) → 5단계 검사
  실패 → 빨간 X, main 보호 규칙으로 머지 버튼 잠김
  성공 → 초록 체크 → 사용자 검수 → Squash and merge
```

## 설계 결정

| 결정 | 선택 | 대안 | 이유 |
|---|---|---|---|
| 프레임워크 | Next.js App Router | Vite+React SPA + 별도 서버 | 화면과 API(Route Handler)를 한 저장소·한 배포로. 서버 컴포넌트로 DB를 서버에서 바로 읽을 수 있고 Vercel과 통합이 좋다 |
| 언어 | TypeScript strict | JavaScript | 타입으로 잘못된 데이터 모양을 컴파일 단계에서 잡는다. 생성 코드의 실수를 기계가 먼저 거른다 |
| UI | shadcn/ui | MUI, Chakra | 컴포넌트 소스를 프로젝트에 복사해 소유. 디자인 수정 자유, 런타임 의존 적음 |
| 단위 테스트 | Vitest | Jest | ESM·TS 설정이 간단하고 빠르다 |
| E2E | Playwright(프로덕션 빌드 대상) | Cypress, dev 서버 대상 | 실제 빌드 산출물로 테스트해야 배포 환경과 같다 |
| 품질 게이트 | CI + main 보호 | 수동 확인 | 사람 검수는 동작 중심, 코드 품질의 바닥은 기계가 보장 |
| 패키지 매니저 | pnpm | npm | 심볼릭 링크 기반 저장소로 설치가 빠르고 디스크 절약 |

## 개념 정리

- **App Router**: `src/app/` 폴더 구조가 곧 URL. `page.tsx`=화면, `layout.tsx`=공통 틀, `route.ts`=API(Route Handler).
- **서버 컴포넌트(RSC)**: 기본적으로 컴포넌트는 서버에서 렌더링되고 HTML만 브라우저로 간다. 비밀키·DB 접근을 서버 컴포넌트에서 해도 브라우저로 새지 않는다. 브라우저 상호작용이 필요하면 `"use client"`.
- **Cache Components (Next 16)**: 페이지/GET 핸들러를 빌드 때 미리 렌더링(정적)하고, 요청 시점 데이터가 필요한 부분만 동적으로 만든다. "기본 정적"이라 DB를 읽는 곳은 명시적으로 동적 처리해야 한다.
- **린트 vs 서식 vs 타입 검사**: 서식(Prettier)은 모양, 린트(ESLint)는 실수 패턴(예: 훅 규칙 위반), 타입 검사(tsc)는 데이터 모양의 일관성.
- **lockfile**: 실제 설치된 의존성의 정확한 버전 기록. CI가 같은 버전을 재현하게 한다.
